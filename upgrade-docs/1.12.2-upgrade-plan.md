# SWC UXP Wrappers — Upgrade Plan: 1.12.1 -> 1.12.2

Generated fresh from the live repo (`packages/*/package.json` + `src/*.js` import grep) and
from `npm pack`/tarball diffs of each `@spectrum-web-components/*` package between 1.12.1 and
1.12.2. Not derived from, or trusted against, any prior status doc.

## Scope

43 wrapper packages currently pinned to `@spectrum-web-components/*@1.12.1` (per
`packages/*/package.json`'s `@swc-uxp-internal/{name}` entry), plus `utils` (shared package
whose `@swc-uxp-internal/*` npm aliases pin several SWC-owned sub-packages at 1.12.1).

Excluded (already on 1.12.2, out of scope for this plan): `action-menu`, `badge`, `breadcrumbs`,
`coachmark`, `dropzone`, `menu`, `picker`, `progress-bar`, `progress-circle`, `slider`.

## Dependency graph note

Built from each package's `dependencies` (`@swc-uxp-wrappers/*` entries) plus a grep of
`src/*.js` for `@swc-uxp-wrappers/{other}` imports not reflected in `package.json`. No mismatch
was found for any in-scope component — the one apparent hit (`slider/src/Slider.js` mentions
`@swc-uxp-wrappers/tooltip` in a comment describing a UXP CSS workaround, not an import; `slider`
is out of scope for this plan regardless since it is already on 1.12.2).

`utils/src/aliases.js` lists essentially every wrapper package name as an alias-map string value
(`'@spectrum-web-components/x': '@swc-uxp-wrappers/x'`). These are not imports/requires and do
not constitute real code dependencies of `utils` on those wrapper packages — they run in the
opposite direction (wrapper packages get aliased to `utils`'s build tooling, not vice versa).
`utils` itself has zero `@swc-uxp-wrappers/*` entries in its own `dependencies` and is placed at
layer 0.

## Upstream diff findings (1.12.1 -> 1.12.2)

`npm pack`'d and diffed every in-scope component's tarball, old vs new version (excluding the
`version` field itself and other packages' version-pin bumps inside `package.json`, which are
expected/mechanical noise on every bump). Result:

- **40 of 43** components show **no functional diff at all** — the only change in their tarball
  is their own `package.json`'s `dependencies`/`peerDependencies` block bumping *other*
  `@spectrum-web-components/*` version pins from 1.12.1 to 1.12.2. No compiled `.js`, `.d.ts`, or
  `custom-elements.json` content changed. These are marked **skip — no upstream changes** below;
  EXECUTE mode still needs to bump the `@swc-uxp-internal/{name}` pin string in each of their
  `package.json`s (and, for `utils`, its several SWC-owned `@swc-uxp-internal/*` aliases:
  `theme`, `base`, `styles`, `shared`, `reactive-controllers`, `icon`, `icons`, `iconset`,
  `icons-ui`, `icons-workflow` — all confirmed pin-bump-only between 1.12.1 and 1.12.2, including
  `base`, whose only non-pin diff is its internal `version`/`coreVersion` string constants), but
  should not run the full analysis/review/demo/test cycle for these — there is nothing to
  review.
- **3 of 43** components have a **real, meaningful upstream diff** — all three are the same kind
  of change: SWC converted a plain `@property`-decorated field into an explicit
  getter/setter-with-backing-field pattern and added a `@deprecated` JSDoc annotation (visible in
  `custom-elements.json` and `.d.ts`) pointing at a 2nd-gen replacement component. No runtime
  behavior changes (the getter/setter pair is functionally equivalent to the old field), but the
  deprecation notice is new public-facing metadata that should propagate into the wrapper's own
  `.d.ts`/JSDoc during EXECUTE mode's review:
  - **action-button**: `emphasized`, `selected`, `toggles` — deprecated in favor of
    `swc-toggle-button` / `swc-toggle-button-group`.
  - **button-group**: `vertical` — deprecated in favor of `orientation="vertical"` on
    `swc-button-group` (2nd-gen).
  - **tooltip**: `self-managed`, `tip-padding` — deprecated, no replacement named yet ("will be
    removed in a future release").

  These three are marked **upgrade** below and should go through the full
  `swc-uxp-upgrade` → `swc-uxp-review` cycle in EXECUTE mode, primarily to decide how (or
  whether) to surface these deprecation notices in the wrapper's own docs/JSDoc — not because any
  UXP compatibility behavior changed.

No wiki cross-check was performed for "new wrapper" candidates in this run (no wiki page was
provided/discussed for this session) — every component in scope already has an existing
`packages/{name}/package.json`, so there are no brand-new-wrapper candidates to flag regardless.

## Merge / Review / Test Order (by layer, lowest first)

**Layer 0** (20 components, no in-scope wrapper deps): button, checkbox, divider, popover,
tooltip, asset, avatar, contextual-help, field-label, help-text, icon, illustrated-message, link,
shared, sidenav, status-light, swatch, theme, thumbnail, utils.

**Layer 1** (13 components, depend only on layer 0): action-bar, action-button, alert-banner,
button-group, card, field-group, infield-button, meter, picker-button, switch, table, tags,
toast.

**Layer 2** (5 components, depend on layer ≤1): action-group, alert-dialog, overlay, radio, tabs.

**Layer 3** (2 components, depend on layer ≤2): dialog, textfield.

**Layer 4** (3 components, depend on layer ≤3): combobox, number-field, search.

Process strictly layer 0 → 1 → 2 → 3 → 4. Within a layer, all components can be
upgraded/reviewed/merged in parallel (no edges between them). `action-button`, `button-group`,
and `tooltip` (the only real **upgrade** actions) fall in layers 1, 1, and 0 respectively, so they
resolve early and don't block anything downstream from needing extra scrutiny beyond their own
layer.
